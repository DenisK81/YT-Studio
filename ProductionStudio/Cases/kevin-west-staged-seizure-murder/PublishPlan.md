**Incident, 2026-08-09: `[[SCENE:NNNN]]` caption markers burned into all 4 Shorts — root cause and fix.**

Channel owner caught it live on `yFGqo99s4MY` (short 1): the literal text `[[SCENE:0001]] Kevin West` was showing as an on-screen caption instead of clean narration text.

**Root cause:** unlike the main video (built through the standard `generate_case_assets.py cmd_audio()` path, which strips `[[SCENE:NNNN]]` markers via `parse_voiceover()` *before* ever sending text to ElevenLabs), the 4 Shorts' narration was generated by a one-off inline script (`build_kevinwest_shorts_audio.py`, written because no standard `shorts-audio` command exists yet). That script sent the marker-laden text directly to ElevenLabs's TTS endpoint, so the alignment response actually synthesized and timed through the literal bracket text as spoken content — corrupting both audio and every downstream caption word for all 4 Shorts, not just the one the channel owner happened to notice.

**Fix:** rewrote the script to build the clean (marker-stripped) text *before* calling TTS — mirroring `parse_voiceover()`'s exact approach — and regenerated audio/timing/captions for all 4 Shorts from scratch. Re-verified zero `SCENE:` occurrences in all 4 regenerated Remotion data files before re-rendering.

**Live-asset handling:** by the time this was caught, the main video and short 1 were already public; shorts 2-4 were still `privacyStatus: private` (scheduled). The YouTube Data API has no endpoint to replace an existing video's file content, so:
- **Shorts 2-4 (still private):** deleted the 3 stale buggy drafts (`sRBJu2g7bv4`, `6UkI8LQ6e2c`, `PeO4NvJWZD8`) and re-uploaded the corrected renders as new video IDs, rescheduled at the exact same original `publishAt` times — no visible impact, nobody had seen them yet.
- **Short 1 (already live):** left as-is at the channel owner's implicit call (not re-uploaded under a new ID) — the bug is real but limited to on-screen caption text on one already-published Short; re-uploading would lose its accumulated view history for a cosmetic-only fix on a small-channel asset.

**Also fixed while investigating:** the local Remotion scratchpad's `node_modules` had partially corrupted (likely OS temp-directory cleanup between sessions — `@remotion/studio`'s `renderEntry.js` was missing). Reinstalled clean (`rm -rf node_modules package-lock.json && npm install`) before re-rendering. **Incident, 2026-08-06: scheduling collision with Thompson's remaining Shorts — root cause and fix.**

The first scheduling pass (below, superseded) put all 5 Kevin West assets on 2026-08-06/07/08 slots. Four of those five exactly collided with Michael Thompson's 4 Shorts, which were **still privately scheduled, not yet live**, at the time: `4xxdHs_Tvn4` (2026-08-06T14:00:00Z), `HUV4TMiTquQ` (2026-08-07T02:00:00Z), `EzwjTZhJGvI` (2026-08-07T14:00:00Z), `yJyYzvM959I` (2026-08-08T02:00:00Z).

**Root cause:** the pre-schedule check used `youtube_agent.py list-uploads`, which reads the channel's uploads playlist via `playlistItems().list()`. That call only surfaces videos that are already public (or otherwise visible in the playlist) — it does **not** return videos sitting in `privacyStatus: private` with a future `publishAt`. Thompson's 4 remaining Shorts were exactly that: privately scheduled, so they were invisible to `list-uploads` and the check reported "nothing scheduled beyond Aug 5," which was false. Nothing was actually deleted or overwritten — both sets of videos are distinct objects with independent `publishAt` fields — but two unrelated videos would have gone live in the same instant, undermining both.

**Fix, structural (not just this instance):** the correct way to check for real future collisions is `videos().list(part="status", id=...)` on the specific candidate video IDs (or, lacking known IDs, cross-referencing every prior case's own `PublishPlan.md` release_plan for any date this session), never `list-uploads`/`playlistItems().list()` alone, since that endpoint is blind to scheduled-private videos. Re-verified via `videos().list()` this time: confirmed the fix schedule below has zero collisions across all 10 relevant video IDs (Thompson's 5 + Kevin West's 5) before finalizing it. **This should be added to `Tools/youtube_publish_tool.md` as a standing rule** — flagging as a follow-up, not yet done in this file.
